# Sandbox Migration Status

This document tracks the active effort to move OpenRhiza from native bootstrap fallbacks toward sandbox-owned capabilities.

Authoritative rule:

- Keep the core as a survival substrate.
- Move drivers, GUI shell behavior, filesystem logic, registry policy, and autonomy planning into sandboxed skills, drivers, workflows, or object capabilities.
- Never promote a sandbox component to live ownership without evidence, validation, and rollback.

## Current Status

ARM64 recovery has been re-shrunk to the iron-law boundary: the default ELF now keeps only PL011 recovery console, basic platform status, and read-only virtio-mmio identity probing. Historical `/virtio-wasm-*`, `/vos*`, `/vospolicy-*`, payload, and GUI experiments are no longer default recovery-core behavior; they must return only as sandbox skills, workflows, or explicit external proof harnesses. Historical evidence below records prior proof work; it is not permission to put those paths back into the recovery core.

## Completed Migration Infrastructure

- Multiple named Wasm modules can be loaded and polled.
- `/wasm-quarantine-selftest` proves the runtime can isolate a deliberately
  trapping Wasm module after three consecutive traps while keeping the recovery
  shell alive.
- `/wasm-quarantine-recovery-selftest` and `/wasm-unquarantine <module_key>`
  prove an operator can explicitly clear quarantine after inspection. The trap
  counter is retained for audit; if the same broken module is retried without a
  repaired artifact it will be quarantined again.
- `/skill-recover <skill_id>` unloads the current sandbox module, resets that
  skill lifecycle to `Bootstrap`, and reloads the cached artifact through the
  normal Testing gate. It is the preferred operator path for retrying a repaired
  or refreshed skill artifact before clearing low-level Wasm quarantine by hand.
  Cache records may now carry `artifact_id`, `version`, `updated_at`, and
  `signature_verified` metadata. Skill downloads verify optional Nexus payload
  signatures before marking a cached artifact as signed. If the cache contains
  duplicate records for one skill, recovery ranks candidates by verified
  signature, version, `updated_at`, then cache order while normal load remains
  stable on the first record. Payload caching is keyed by both `skill_id` and
  FAT artifact name, so a replacement candidate cannot accidentally reuse stale
  Wasm bytes. The QEMU smoke `logs\skill-recover-signed-metadata-cli.log`
  passed for `skill_qemu_driver_pack_v1` and reloaded `SK008.WAS` to `Testing`.
  `/skill-cache-rank-selftest` also passed in QEMU, selecting the signed
  fixture artifact `SK024.WAS` with `signature_verified=1` over unsigned and
  older duplicate candidates.
- Loaded skill exports can be invoked explicitly through `/skill-invoke <skill_id> <export>`, which allows dangerous live-preparation exports such as e1000/xHCI cutover probes to remain manual and non-autorun.
- Driver host ABI exposes handle-scoped PCI config, MMIO, PIO, DMA, IRQ access.
- Probe-only driver handles can be released after validation.
- Driver-host handles now have heartbeat leases; stale device authority is automatically released.
- e1000 has `native-fallback`, `sandbox-candidate`, and gated `sandbox-active` stages.
- e1000 sandbox candidates can submit non-disruptive lease heartbeats, verify DMA descriptor memory readback, prove sandbox-owned RX/TX descriptor layout against bounded DMA memory, expose a non-autorun live descriptor-ring cutover entrypoint, and contain a live `poll_net` path for TX descriptor submission and RX descriptor harvesting after cutover. `/net-e1000-cutover` and `/net-sandbox-cutover <skill_id> <driver_id>` are the first core-owned handoff gates: they quiesce native fallback, invoke the cutover export, poll sandbox TX/RX, then promote or roll back.
- xHCI sandbox candidates can build and verify event-ring DMA layout. `/xhci-sandbox-prepare` runs the candidate and calls a recovery-safe event-ring prepare export while forcing keyboard/mouse routing back to native handoff-mirror fallback. The dangerous register-writing `commit_live_xhci_event_ring` export is isolated and not used by autorun or normal prepare. `/xhci-rollback-drill` is the only manual path that calls it, and it immediately reinitializes native xHCI fallback instead of promoting sandbox input ownership. It is QEMU-verified with keyboard input still accepted after the drill.
- Storage has `native-fallback`, `sandbox-candidate`, and gated `sandbox-active` stages.
- Storage sandbox candidates can submit lease heartbeats and now prove PIIX PIO read plus scratch write/read/restore. ## Promotion Policy

A sandbox component may become active only if all of these are true:

- It has a stable identity and match key.
- It runs in the sandbox and uses handle/object-scoped host calls.
- It reports objective health evidence.
- The core validates that evidence independently where possible.
- Recovery fallback remains available.
- Rollback has been tested or is mechanically available.
- It keeps submitting lease heartbeats after promotion; otherwise the core reverts to a safe fallback.
- The promotion is tied to one object, not global mutable state.
