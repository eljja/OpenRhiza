# OpenRhiza 새 개발 로드맵

[영문 원문](ROADMAP.md) · [한국어 목차](../README.ko.md)

기존 런타임 구현이나 완료 이정표를 승계하지 않는 계획입니다. 과거 커널·Nexus·증명 작업은 참고 자료입니다.
[방향 문서](DIRECTION.ko.md)가 기준이며 요구사항 ID는 [요구사항 문서](REQUIREMENTS.ko.md)를 따릅니다.

Astra 검토 보완은 [구현 착수·통과 기준](IMPLEMENTATION_GATES.ko.md)에 반영했습니다.
아래 조건 이름은 그 문서를 가리키며 아직 통과한 조건은 없습니다.
커널 코드는 사용자가 지정한 `gpt-6-astra`로 구현하고 빌드·QEMU·장애 주입·수정으로 검증하며 조건별로 보고합니다.

## 재시작 지점 R0

R0는 소스 목록, 의도 취합, 아키텍처 결정, 기존 교훈, 개발 경계, 새 시험 순서를 정합니다.
새 커널 이미지, 프로세스 격리, 모듈 로더, 전송 ABI, 공개 릴리스는 구현하지 않았습니다.
기존 QEMU 기본 동작 시험은 별도로 보고하며 새 단계의 진척으로 계산하지 않습니다.

새 작업은 `next/`에 둡니다. 기존 소스 이동·삭제나 로컬 변경 되돌리기를 하지 않습니다.
상위 Cargo 패치, 호스트에서 주입한 키, 기존 바이너리 시험 자료를 가져오지 않습니다.
커널·모듈·SDK·레지스트리/제작 환경·스키마·시험은 새 소유권과 독립 빌드를 갖습니다.
검토한 표준·이식 가능한 의존성은 라이선스·고정 버전·출처와 함께 명시적으로 선정합니다.

## 검증된 실행 환경의 6단계

명시한 환경에 대해 단계 순서를 유지합니다. 2.3은 별도 SMP 검증입니다.
단일 vCPU 환경은 2.1~2.2 통과 후 3단계로 갈 수 있지만, 2.3 통과 전 SMP는 미구현·미검증으로 명시합니다.
검증되지 않은 SMP를 켜거나 전체 SMP 단계가 완료됐다고 주장할 수 없습니다.

### 1단계: 새 부팅과 재현 가능한 기반

요구사항: R01-R03, R14, R24-R25.

**1.1:** 짧은 검토된 ADR(아키텍처 결정 기록)과 시험 자료로 K를 충족합니다.
x86_64 QEMU·펌웨어·도구체인 구성 하나, 부트 신뢰·파서·제한된 메모리 인계, 첫 주체의 권한,
상주 복구 의존성·예약 개요, 자원 소유권, 초기 네이티브 ABI·오류 형식, 기본 장치 거부,
독립 시험 도구·초기 기한을 정합니다. 최소 격리 비-DMA 복구 콘솔 계약을 검토합니다.
자격증명·시험 키 규칙을 기록합니다. 수정된 기존 부트로더나 상위 Cargo·도구체인 설정을 승계하지 않습니다.
검증한 부트 형식과 초기 시험 자료만 확정하고, 나머지 매니페스트·네이티브 ABI는 구현 부분집합의 왕복 시험까지 실험 상태로 둡니다.
1.1단계의 K는 아직 통과하지 않았습니다.

**1.2:** 독립 워크스페이스·이미지 빌더를 만들고 새 커널 진입, 초기 진단, 메모리 맵 검사,
IDT·장애 스택 기반, 타이머, 제한된 진단 기록을 추가합니다. 모든 unsafe 경계를 설명합니다.
제품 기능 코드는 넣지 않습니다. K의 선택과 진입 검토가 기록된 뒤 시작합니다.

**1.3:** 깨끗한 체크아웃에서 빌드하고 새 QEMU 시험 도구로 세 번 부팅합니다.
도구·펌웨어 버전, 소스·이미지 해시, 명령줄, 부팅 식별자, 직렬 로그, 시간 초과·종료 상태,
의도적 커널 패닉 진단을 기록합니다. 패닉 시험은 진단·복구 동작만 입증하며 동일 코어 생존은 입증하지 않습니다.
외부 부팅·리셋 판정기와 미리 정한 호스트 기한을 사용합니다. 초기 보정 후보는 새 부팅당 30초이며 수락시험 전에 검증합니다.

통과 조건: 재현 가능한 새 이미지, 정확한 실패 기록, 의존성·경계 검토.
기존 이미지가 부팅된다는 이유로 2단계를 시작하지 않습니다.

### 2단계: 보호된 실행과 모듈 생존

요구사항: R02-R03, R08, R13-R14, R25.

**2.1:** 단일 CPU에서 N을 구현합니다. 소유권 있는 페이지 할당, 보호 주소 공간·스택, 네이티브 ELF 진입·복귀,
선점, 제한된 시스템 호출·IPC, 주체별 핸들을 갖춥니다. 적대적 실행 전에 자원 부담 주체·한도,
철회·회수 완료, 요청 스냅샷, 상대 종료, 취소, 우선순위 역전 한도를 정합니다.
인증된 고정 초기·복구 집합, 보호 예약 자원, 격리된 로거·터미널·감독자, 작은 결정적 명령 레지스트리를 추가합니다.

N 통과 조건: 격리 프로세스 네 개가 독립적으로 주어진 확인 작업을 실제 완료합니다.
잘못된 포인터·명령어, 나눗셈 오류, 스택 넘침, 무한 루프, 메타데이터·힙 고갈, 핸들·IPC 경쟁,
일반 감독자 충돌에도 부팅 식별자·관계없는 작업·복구가 유지됩니다.
수치 기한, L/L+1 허가 동작, 원장 기준치, 반복 회수 검사를 미리 정합니다.
의도적 실패 대조군에서 시험 도구가 실패해야 합니다. 미검증 장치 권한은 주지 않습니다.

**2.2:** N 이후 격리된 Wasm 작업자·중개기 환경 하나의 버전을 고정하고 W를 통과합니다.
실제 작업자 경로로 런타임·호스트 호출 실패, 할당량 고갈, 선점을 시험합니다.
데스크톱용 런타임 기본 기능이 그대로 사용 가능하다고 가정하지 않습니다.

**2.3:** SMP 활성화 전에 두 vCPU에서 동시 소유권, TLB 무효화·확인, 인터럽트,
회수·재사용, 아키텍처 상태를 따로 검증합니다. 2.1~2.2의 단일 vCPU 통과와 미완료 SMP를 구분해 보고합니다.
어느 환경이든 watchdog 재부팅은 격리 실패입니다.

### 3단계: 실제 서비스와 안전한 모듈 공급

요구사항: R04, R10-R15, R24-R25.

**3.1:** 일반 장치 직접 권한 전에 D를 충족합니다. 정확한 DMA·요청자·도메인·MMIO·인터럽트 격리,
코어 타이머 독립성, 리셋·접근 종료 확인, 제한된 격리를 갖춥니다.
드라이버 종료·버퍼 재사용 중 금지 주소 접근, IRQ 폭주, 늦은 I/O를 주입합니다.
강제 가능한 격리가 없으면 적대적 드라이버 격리를 주장할 수 없습니다.
그 뒤 재시작 가능한 장치 관리자와 격리된 VirtIO 블록·네트워크 모듈을 도입합니다.

**3.2:** 네트워크 소비자보다 먼저 A의 최소 신뢰·시간·엔트로피 계약을 구현합니다.
고정 이미지 신뢰는 실제 시각에 의존하지 않습니다. 동적 등록·TLS·키 생성은 선정된 신뢰·실패 정책이 필요합니다.
오프라인 설치 기능의 권한, 오래된 메타데이터, 철회, 허용 롤백, 영속 보안 세대를 정합니다.
DHCP/DNS/TLS/소켓과 탐색·캐시 모듈을 추가합니다. 커널에 형식 파서나 레지스트리 조정 로직을 넣지 않습니다.

**3.3:** 실제 파일·디렉터리·이름 변경·flush·복구를 제공하는 VFS와 작은 영속 파일시스템을 추가합니다.
사용자 데이터 쓰기나 실제 전환 전에 수명주기 세대, 기존 작업 차단, 확정 시점, 호환 상태 이전,
중단 시 허용 상태를 정합니다. 블록·캐시 가정 아래 쓰기 유실·순서 변경·부분 기록을 주입하고
호스트 데이터·신뢰 판정기와 비교합니다. 재부팅만으로는 충분하지 않습니다.

공통 스키마를 중심으로 인증된 등록, 불변 산출물·해시·매니페스트·서명, 채널, 소유권, 철회를 갖춘 최소 Nexus를 새로 만듭니다.
독립 시험한 인공 패키지부터 사용하며 비신뢰 생성 코드는 아직 도입하지 않습니다.
레지스트리가 침해되어도 로컬 허가가 정책·권한·예산을 강제합니다.
3.3에서 최소 신뢰 상태 영속화·복구가 검증될 때까지 외부 등록·설치를 비활성화합니다.
네트워크 프로토콜 개발만으로 외부 패키지 허가가 가능해지는 것은 아닙니다.

통과 조건: 실제 파일 내용이 재부팅·전원 손실 주입 후 유지됩니다.
잘못된 TLS 상대, 서명 없음·손상·철회·재전송 패키지를 거부합니다.
서명 모듈 다운로드, 오프라인 캐시 재실행, 실제 서비스·장치 전환이 동작합니다.
드라이버 충돌 시 자원 철회·장치 리셋 또는 복구 진입이 코어 손상 없이 이루어집니다.

### 4단계: 멀티태스킹 데스크톱과 네이티브 SDK

요구사항: R05, R07-R08, R17, R19-R20, R25.

사용자 모드 화면·입력·텍스트 모듈, 공유 화면 표면·변경 영역, 네이티브 합성기, 포커스·포인터 캡처,
창·문서 수명주기, 작업 공간, 실행기, 클립보드, 알림, 접근성 텍스트를 제공합니다.
한·영 폰트·IME·조합은 커널이 아닌 서비스로 제공합니다.
네이티브 SDK와 실제 데이터·백그라운드 작업을 가진 독립 터미널·파일·설정·모니터·모듈 관리자 프로세스를 만듭니다.

통과 조건: 최소 다섯 앱이 동시 실행됩니다. 합성 입력과 화면·상태 검사로 포커스, 끌기·크기 변경,
최소화·복원, MDI·작업 공간 전환, 닫기를 확인합니다.
앱·합성기·화면 장애에도 복구와 다른 작업의 예산이 유지됩니다.
8시간 시험에서 입력 지연·메모리·큐·자원을 측정하고 환경별 지연·자원 증가 한도를 미리 정합니다.
이름이나 상태 표시만으로 통과하지 않습니다.

### 5단계: AI 작업과 완전한 앱 데모

요구사항: R04, R06-R07, R09-R10, R12, R16-R18, R20-R21, R25.

제공자 중립적인 제한된 모델 작업과 보호된 비밀정보로 기존 로컬 작업 레지스트리를 확장합니다.
타입 계획, 결정적 정책·승인, 트랜잭션, 취소, 감사, 되돌리기를 추가합니다.
Intent를 충족합니다. 승인 효과를 주체·객체 세대·인자·정책 세대에 연결해 확정 시 재검증하고
대상 교체·철회·재전송·확인 위조를 시험합니다.
버전을 고정한 빌드 환경, 생성자가 바꿀 수 없는 시험, 독립 승인된 서명, 로컬 시험 배치를 사용하는 격리 제작 작업자를 추가합니다.

권한 기반 의미 그래프·질의·갱신, 선택적 보조·협의 모드, 녹음 상태가 보이는 누르고 말하기의
오디오·VAD·ASR·전사문 모듈을 추가합니다. 직접 음성·상시 청취는 이후 선택 기능으로 둡니다.
SDK·빌드를 점진적으로 OS 안에 옮기며, 자가 개발 조건을 통과할 때까지 외부 제작 도구를 개발 의존성으로 표시합니다.

레지스트리에서 Doom 엔진과 별도 라이선스 FreeDoom 콘텐츠를 설치합니다.
35 Hz 시뮬레이션, 포커스에 맞는 입력, 빈 화면이 아닌 출력, 소리, 재부팅 후 저장·불러오기,
백그라운드 일시정지·속도 제한, 오프라인 실행, 삭제, 장애 격리를 시험합니다.
공유 버퍼·일괄 처리·격리된 AOT·네이티브 작업자로 최적화하되 게임 분기를 코어에 넣거나
프레임 수치를 위해 네트워크·복구를 굶기지 않습니다.

통과 조건: 생성된 비특권 모듈이 독립 실패 시험과 시험 배치·롤백을 통과합니다.
문서·도구·모델 출력의 주입 공격이 권한을 얻지 못합니다.
음성 거부·취소·개인정보와 의미 지식 권한이 유지되고, 미리 정한 게임 시간·오디오·응답성 허용치를 충족합니다.
오프라인 설치 앱과 직접 명령도 계속 사용할 수 있어야 합니다.

### 6단계: 검증된 공개 시스템과 생태계

요구사항: R10-R12, R14-R15, R22-R25.

서명 시스템·모듈 릴리스, 출처·SBOM·라이선스, 키 교체·철회, A/B 업데이트,
데이터 이전·백업·복원을 갖춥니다. 기여자·관리자·서명자 역할, 근거 수집, 남용·비용 통제,
검토·조정, 공개·비공개 표현, 배포·DB 백업·롤백, 보안 보고를 검증합니다.

퍼징·적대적 검토, 수일간 장시간 시험, 설치·업데이트 중단, 반복 업그레이드·롤백을 수행합니다.
실제 PC 지원을 주장하려면 명시한 한 기종을 검증합니다. 그렇지 않으면 시험한 QEMU 범위로 공개합니다.
보편적 호환성 대신 정확한 지원 기능·제한·근거·복구 절차를 공개합니다.

통과 조건: 서명된 업그레이드 두 번과 롤백, 철회·낮은 보안 버전·손상 산출물 거부,
업데이트 중단 후 영속 복구, 근거와 연결된 공개 레지스트리,
명시한 범위에 미해결 치명적 보안 문제나 조용한 데이터 손상이 없어야 합니다.

## 보존한 확장 과제

폭넓은 외부 파일시스템, 완전한 자가 Rust/C 도구체인, 브라우저·연구 흐름, 로컬 모델·GPU/NPU,
Wi-Fi·Bluetooth·USB 테더링, 노트북 전원·절전, 가속 그래픽, ARM64 QEMU·검증 보드,
RISC-V, 잠금 해제 폰 한 기종, 외부 프로그램 런타임, Wayland/KDE/GNOME 호환성은 계속 목표입니다.
초기 QEMU 이정표 완료의 선행 조건은 아니며 각자 모듈 계약·통과 표를 갖습니다.

## 진행 보고 규칙

각 프롬프트 시작 시 새 기준의 현재 단계·세부 단계, 기존 변경 보존 범위, 마지막 새 빌드·QEMU 근거,
이번 목표·통과 조건을 보고합니다. 끝날 때 변경 파일, 시험 명령·결과, 정확한 QEMU 환경·로그,
제한, 다음 단계 진입 가능 여부를 보고합니다. 기존 참고 근거와 새 근거를 구분합니다.
검증한 vCPU·장치 환경과 미룬 SMP·장치 조건도 명시합니다.

새 런타임 QEMU 근거 없이 단계 통과를 선언하지 않습니다. 문서·호스트 시험은 준비 작업을 완료할 수 있지만 OS 단계를 완료하지 않습니다.
실패한 조건은 실패로 남기고 진단 근거를 보존하며 원인을 좁힌 뒤 진행합니다.

바로 다음 작업은 1.1단계입니다. 명시적으로 검토한 선택·시험 자료로 K를 충족한 뒤 Astra로 1.2 커널 구현을 시작합니다.
계획 검토 반영만으로 구체적 계약을 선정하거나 런타임 조건을 통과한 것은 아닙니다.
